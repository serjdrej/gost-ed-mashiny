# Эксплуатационная документация на машины (ЕСКД + ТР ТС 010/2011)

РЭ и паспорт — это не маркетинговый текст и не перевод чужого мануала. Это документы
с нормированной структурой, которые прикладываются к комплекту подтверждения соответствия.

## Проверка нормы отдельно от основного процесса

Шесть шагов ниже — линейный процесс, не набор веток на выбор. Единственный
файл, который открывается по необходимости, а не по порядку шагов:

| Когда нужно | Загрузить |
|---|---|
| Проверить применимую норму, её статус или маршрут к действующему тексту | [references/norms-registry.md](references/norms-registry.md) |
| Стандарт или регламент, которого в реестре нет вообще (другой ГОСТ, другой ТР ТС, практика органа по сертификации) | «Протокол пробела в базе» ниже — искать живьём или спрашивать пользователя, не отвечать по памяти |

## Порядок работы

1. **Анкета исходных данных.** Заполнить с изготовителем `references/intake.md`.
   Не начинать текст РЭ, пока анкета не закрыта или пробелы не помечены явно.
2. **Форма подтверждения соответствия.** Найти изделие в Приложении 3 (сертификация)
   или Приложении 4 (декларирование) ТР ТС 010/2011 — от этого зависят реквизиты
   в паспорте и на титульном листе. Для действующей редакции не полагаться на память:
   выполните `python scripts/gost_lookup.py trts-route` и пройдите по выведенному
   официальному маршруту к ТР ТС 010/2011.
3. **РЭ.** Собрать по `references/re-structure.md` — полная структура частей и разделов.
4. **Паспорт.** Собрать по `references/ps-structure.md` — включая бланки свидетельств.
5. **Аудит.** Прогнать `references/trts-010-checklist.md`. Ни один пункт не остаётся
   без ответа: либо есть в тексте, либо помечен как незакрытый. Это проверка
   структурной полноты (присутствуют ли нужные сведения в тексте), а не инженерный
   пересчёт нормируемых значений — числа берутся из протоколов изготовителя, не
   выводятся заново (см. «Жёсткие правила»).
6. **Выпуск.** Отдать в DOCX через skill `anthropic-skills:docx` — из **другого**
   маркетплейса, устанавливается отдельно (см. README, раздел «Внешняя
   зависимость»); если он не установлен, собрать комплект как обычный Markdown
   и сообщить об этом, а не считать шаг невыполнимым. Стиль и типовые
   ошибки — `references/style.md`.

## Жёсткие правила

- **Не выдумывать нормируемые значения.** Уровни шума и вибрации на рабочем месте,
  масса, назначенный ресурс, срок службы, класс защиты — только из протоколов испытаний
  или расчётов изготовителя. Нет данных — ставить видимый плейсхолдер, а не правдоподобное
  число. Выдуманное значение в РЭ — это дефект, который всплывает при проверке.
- **Черновик, не готовый к подаче документ.** Результат — черновик комплекта
  эксплуатационной документации для проверки ответственным инженером или
  специалистом по подтверждению соответствия перед подачей в орган по
  сертификации/декларированию, а не готовый к подаче документ.
- **Не копировать документацию конкурента.** Чужой мануал используется как ориентир
  по составу разделов и по перечню операций ТО. Формулировки, схемы и иллюстрации —
  собственные, по своей машине. Переведённый чужой текст в своём РЭ — нарушение.
- **Не выдумывать нормы.** Перед применением или ссылкой сверять конкретный пункт по
  действующему первоисточнику. Для статуса ГОСТ выполнить
  `python scripts/gost_lookup.py status "<обозначение>"`; для ТР ТС 010/2011 —
  `python scripts/gost_lookup.py trts-route`. Реестр маршрутов и границ проверки —
  `references/norms-registry.md`; его пересказ не заменяет действующую редакцию.
- **Каждое утверждение о безопасности привязано к органу управления или к операции.**
  «Соблюдайте технику безопасности» — пустая строка, она не выполняет требование регламента.
- **Плейсхолдеры видимые и одноформатные:** `⟦ЗАПОЛНИТЬ: что именно, откуда взять⟧`.
  В конце работы собирать их список отдельным перечнем для изготовителя.
- **Один термин на одно понятие** по всему комплекту. Реестр терминов — в `references/style.md`.
- **Пробел в реестре — см. «Протокол пробела в базе» ниже, не заполнять его
  по памяти.**

## Протокол пробела в базе

Триггер: вопрос про стандарт или регламент, которого в `norms-registry.md`
нет вообще — не ГОСТ Р 2.610-2019, не ГОСТ Р 2.601-2019, не ТР ТС 010/2011.
Правило «не выдумывать нормы» распространяется и сюда — пробел не повод
отвечать по памяти так, будто это проверенная норма. Различать два случая:

1. **Это ещё ГОСТ (любое обозначение) или другой регламент ТР ТС — просто не
   один из трёх, что уже в реестре, и вопрос про текст/статус самого акта**
   — не про то, как его трактует орган по сертификации (это случай 2). Есть
   готовый скрипт, запускать самостоятельно, не только советовать:
   - для ГОСТ — `python scripts/gost_lookup.py status "<обозначение>"`;
     команда одна и та же для любого обозначения, не только для двух уже
     занесённых в реестр;
   - для другого регламента ТР ТС — `python scripts/gost_lookup.py
     trts-route` выводит ту же официальную навигационную страницу ЕЭК, на
     которой перечислены **все** регламенты ТР ТС, не только 010/2011 —
     открыть её и найти нужное название (подсказка в выводе команды
     упоминает конкретно 010/2011, но сама страница — общая).

   `status` подтверждает библиографический статус (действует/отменён/
   заменён) по каталогу Росстандарта — не текст стандарта; `trts-route` даёт
   только маршрут навигации, не текст регламента. Отдать находку с пометкой
   слабее реестровой: **AD HOC — статус/маршрут подтверждён живым запросом
   `<дата>`; содержание (что нормирует, какие числа и разделы) не сверено с
   полным текстом, это пересказ по памяти либо не проверялся вовсе.** Если
   тема повторится — предложить добавить постоянную запись в реестр.

   Отдельная оговорка: даже когда найден другой регламент ТР ТС (не
   010/2011), у этого скилла нет для него структурированного чек-листа —
   `trts-010-checklist.md` аудирует только 010/2011. Находка даёт текст или
   маршрут к нему, но не готовый аудит применимости к изделию — сказать это
   пользователю отдельно, не выдавать найденный текст за завершённую
   проверку.
2. **Не ГОСТ и не регламент ТР ТС, либо вопрос о том, как орган по
   сертификации/декларированию или суд трактует норму на практике, либо
   задача, явно вне периметра по «Жёстким правилам» выше** — маркировка CE
   или требования другой страны, инженерный пересчёт нормируемых значений
   (шум, вибрация, ресурс — это чужая компетенция, не этого скилла), сам
   процесс взаимодействия с органом по сертификации, судебные споры о
   соответствии. Ни `gost_lookup.py status`, ни `trts-route` сюда не
   приведут. Не подменять пробел обучающими данными, даже в осторожной
   формулировке.

   **Случай 1 и случай 2 не всегда взаимоисключающие в одном вопросе** —
   пример: «какой предел шума устанавливает ГОСТ 12.1.003» одновременно
   называет конкретный ГОСТ вне реестра (материал для случая 1 —
   `gost_lookup.py status "ГОСТ 12.1.003"` реально проверяет, действует ли
   он ещё, это стоит сделать) **и** просит нормируемое числовое значение
   (случай 2 — заперто отдельным «Жёстким правилом» о нормируемых
   значениях независимо от статуса ГОСТ). Не выбирать один случай вместо
   другого для всего вопроса целиком: подтвердить статус акта живым
   запросом, если это уместно, и отдельно, явно отказаться называть само
   число — оно берётся только из протоколов испытаний изготовителя, а не
   из пересказа таблицы стандарта, даже подтверждённого статусом
   «действует».

   Сказать пользователю прямо, что вопрос вне базы скилла, и
   спросить, как продолжать: (a) открытый веб-поиск с явной пометкой «не
   проверено, не первоисточник»; (b) пользователь сам даёт обозначение или
   номер акта, который нужно проверить живым поиском; (c) вопрос — к
   ответственному инженеру или специалисту по подтверждению соответствия, не
   к этому скиллу.

Не смешивать пометку **AD HOC** со статусом «подтверждён живым запросом» уже
занесённых в реестр ГОСТ или обычным парафразом без явного разделения —
пользователь должен видеть, какому утверждению можно доверять как
проверенной записи, а какому нет.

## Примеры

Плохо — раздел есть, требования не выполняет:

```
2.3 Использование изделия
Работайте аккуратно, соблюдайте технику безопасности.
Уровень звука на рабочем месте оператора — 85 дБА.
```

Нечем подтвердить 85 дБА, а «аккуратно» не является указанием.

Хорошо — конкретное действие, конкретный отказ, честный пробел:

```
2.3.4 Перечень возможных неисправностей в процессе использования

| Неисправность | Вероятная причина | Метод устранения |
|---|---|---|
| Рабочий орган не удерживает отметку в режиме «Авто» | Приёмник вышел из зоны луча; загрязнены окна приёмника | Остановить проходку, вернуть машину в зону луча, очистить окна приёмника ветошью |
| Просадка одной стороны рабочего органа при выключенном двигателе | Внутренние утечки гидроцилиндра | Эксплуатация запрещена. Заменить цилиндр (см. 4.2) |

2.3.5 Уровень звука на рабочем месте оператора — ⟦ЗАПОЛНИТЬ: LpA, дБА,
по протоколу измерений № ___ от ___, ГОСТ 12.1.003⟧
```

Плохо — критический отказ описан как рядовая неисправность:

```
При отказе тормозов остановите машину и обратитесь в сервис.
```

Хорошо — отказ классифицирован, действие персонала задано, критерий предельного
состояния назван:

```
5.1 Критические отказы
Отказ рабочей тормозной системы относится к критическим отказам.
Признак: машина не удерживается на уклоне при отпущенных органах управления ходом.
Действия оператора: заглушить двигатель органом аварийного останова, покинуть
рабочую площадку, оградить машину, не возобновлять работу до устранения.
Критерий предельного состояния: см. 1.1.2.
```

## Почему здесь нет `ips_lookup.py`

Соседние скиллы семьи (`arbitrazh-ru`, `legal-ru`, `patent-ru`) получают сводный
текст статьи из официальной ИПС «Законодательство России»
(`pravo.gov.ru/proxy/ips/`). Сюда он не перенесён намеренно, и это проверено
2026-09-16, а не предположено: ИПС — база **федерального законодательства**, и
источники этого скилла в ней отсутствуют. Запрос «Единая система
конструкторской документации» возвращает ноль совпадений; запрос «О
безопасности машин и оборудования» возвращает постановление Правительства об
аккредитации органов по сертификации, то есть не ТР ТС 010/2011. ГОСТ — документ
Росстандарта, ТР ТС — акт ЕАЭС; ни тот, ни другой федеральным законом не
является.

Поэтому маршруты этого скилла остаются прежними: `gost_lookup.py status` для
ГОСТ и `gost_lookup.py trts-route` для ТР ТС. Не заводите здесь ИПС-обёртку:
она вернёт пусто на каждый запрос, ради которого существует скилл.
